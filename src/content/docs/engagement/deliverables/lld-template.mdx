## When to use this

Produce the Detailed Technical Design after the Solution Architecture Design is signed and before you deploy production Azure resources. It is the build and operations source of truth for configuration, identity, networking, and release control.

## Inputs you need from the customer

| # | Input | Source | Format |
| --- | --- | --- | --- |
| 1 | Signed Solution Architecture Design | Previous phase | PDF |
| 2 | Well-Architected Framework findings | Assessment workshop | Workbook |
| 3 | Assigned subscriptions, landing zone constraints, and naming standards | Customer cloud team | Document |
| 4 | Tagging policy and release tooling state | Customer cloud team | Document |
| 5 | Security, compliance, and support requirements | Customer security and operations | Document |

## Document structure

<Steps>
1. **Document control and baseline assumptions.**
2. **Resource inventory** — every Azure resource, region, SKU, owner, and lifecycle note.
3. **Sizing and capacity** — token throughput, index size, compute profile, storage, and scale rules.
4. **Network and access design** — virtual networks, private endpoints, DNS, managed identities, and role assignments.
5. **Data and AI design** — model deployments, prompt controls, grounding stores, evaluation, and content filters.
6. **Application configuration and secrets** — environment variables, Key Vault references, feature flags, and policy controls.
7. **Observability and operations** — dashboards, alerting, KQL, runbook hooks, and support procedures.
8. **CI/CD and test design** — pipelines, promotion gates, quality checks, and rollback.
</Steps>

## Output: customer-ready deliverable

A signed Detailed Technical Design in PDF plus the matching infrastructure-as-code or application release tag so the design and deployed implementation stay aligned.

## What the Auditor Checks

The auditor is validating that your organisation can deliver production AI applications on Microsoft Azure, not just run proof-of-concept demos. They expect to see real solution delivery evidence spanning architecture, security, responsible AI, operations, and customer outcomes.

Strong evidence for this control shows repeatable delivery capability across the full lifecycle: discovery, solution architecture, build, evaluation, go-live, and operational handover. The best submissions combine customer case studies with concrete architecture artefacts, implementation standards, and reusable delivery assets.

## Implementation Guidance

### What “good” looks like

- Use case studies that clearly state the business problem, the Azure services selected, the operating model, and the measurable outcome.
- Show how the workload is secured: Microsoft Entra ID, managed identities, Azure Key Vault, network isolation, logging boundaries, and access controls.
- Demonstrate how you evaluate and operate the solution after go-live, especially for Retrieval-Augmented Generation (RAG), agentic workflows, prompt changes, and content filtering.
- Reuse the same terminology across your architecture diagram, Solution Architecture Design, runbook, and evidence tracker so the auditor can follow the control story quickly.

### Architecture patterns to evidence

<Steps>
1. **Front door and orchestration** — show how users or channels enter the system through Azure Front Door, App Service, Azure Container Apps, or Azure Kubernetes Service (AKS), then how application services orchestrate prompts, tools, or model calls.
2. **Model and inference layer** — identify Azure OpenAI deployments, model versions, fallback strategy, throttling behaviour, and whether you use pay-as-you-go or Provisioned Throughput Units (PTU).
3. **Knowledge and grounding layer** — show Azure AI Search, Cosmos DB, Azure SQL, PostgreSQL, or Fabric where relevant, including indexing and update flows.
4. **Security and governance** — include Microsoft Entra ID, managed identities, Key Vault, private endpoints, content safety, and least-privilege role assignments.
5. **Observability and operations** — show Application Insights, Azure Monitor, log analytics, quota alerts, evaluation pipelines, and incident response hooks.
</Steps>

### Real Azure guidance the auditor will expect you to understand

- **Azure OpenAI Service**: document model choices, deployment names, backup deployments, quota assumptions, and prompt or system-message change control.
- **Azure AI Foundry**: show how you manage experimentation, evaluation, prompt flows, and reusable project assets when you use Foundry in the delivery model.
- **Azure AI Search**: explain the chunking, indexing, freshness, access filtering, and relevance-tuning approach for Retrieval-Augmented Generation workloads.
- **Application platform**: explain whether you chose App Service, Azure Container Apps, or AKS, and why that hosting choice fits scale, networking, and operations needs.
- **Responsible AI**: include prompt-injection mitigations, content filter design, human review checkpoints, and post-deployment monitoring for quality and harm signals.

<Aside type="tip">
  Your strongest evidence package is usually one architecture-heavy flagship customer plus one second customer that proves the capability is repeatable in a different industry, workload type, or integration pattern.
</Aside>

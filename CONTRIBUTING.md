# Contributing to the AI Applications on Microsoft Azure specialization toolkit

Thanks for contributing. This repository is the practice's source of truth for the **AI Applications on Microsoft Azure Advanced Specialization** — covering both audit evidence and the productised engagement playbook. Every consultant who runs an engagement is expected to leave the toolkit better than they found it.

The consultant-facing summary of this file is published at [`/innersource/contributing/`](src/content/docs/innersource/contributing.mdx).

## Ground rules

1. **No customer-identifying data.** Replace customer names with `Customer A`, `Customer B`, etc. Redact commercial detail. This applies to issues, PRs, commits, screenshots, and downloadable workfiles.
2. **No fabricated audit content.** Control numbers, evidence requirements, and ACR thresholds must come from the official Microsoft guide. If unsure, leave a `:::caution TODO confirm from official guide:::` callout — never invent.
3. **No content that conflicts with the Microsoft Responsible AI Standard.**
4. **MDX rules apply.** See [`.github/memories/mdx-content.md`](.github/memories/mdx-content.md). The build will fail if you break them.

## Branching

- Default branch: `main`
- Branch naming:
  - `improve/<short-topic>` — generic improvements
  - `lesson/<engagement-slug>` — a real-world lesson learned
  - `fix/<short-topic>` — bug or typo fix
  - `audit-refresh/<year>` — annual audit checklist reconciliation

Commit directly to `main` is permitted for the repo maintainer doing scaffolding work. All other changes go through a PR.

## Issue templates

Use one of the three templates in `.github/ISSUE_TEMPLATE/`:

| Template | Use for |
|---|---|
| `control-improvement` | Changes to a Module A or Module B audit control page |
| `template-improvement` | Changes to an engagement playbook page or downloadable workfile |
| `lesson-learned` | A real-world story tied back to a control or playbook step |

## Pull requests

- One topic per PR. Split unrelated changes.
- Fill in the PR template. It asks for the engagement phase, the control reference, and whether the change is sourced from a real engagement.
- Run `npm run build` locally before pushing.
- Wait for one approval from the area's `CODEOWNERS` entry. Default review SLA: **3 business days**.
- Squash-merge. The squash commit message becomes the changelog entry.

## Workfiles (`public/templates/**`)

Workfiles (`.docx` / `.pptx` / `.xlsx`) are regenerated by the scripts under `scripts/workfiles/`. If you change the MDX page that documents a workfile, also update the generator script and re-run it so the downloadable stays in sync.

```powershell
python scripts/workfiles/generate_all.py
```

## Local development

```powershell
npm install
npm run dev
```

Build that mirrors CI:

```powershell
npm run build
```

## Code of conduct

Be specific, be kind, and assume good intent. Disagreement on a design decision is healthy; personal attacks are not. Escalate disputes to the repo maintainer.

## Release & versioning

The site is built and deployed on every push to `main` by `.github/workflows/deploy.yml`. There is no semver — `main` is the release. The annual audit refresh tags `audit-YYYY` for traceability.
